# 🌲 邻接表建树的数学本质与逻辑推导

## 1. 核心困惑：邻接表存的是“图”，为什么能直接拿来当“树”用？

在代码中，我们用 `vector<vector<int>> g(n + 1)` 读入边时，对每条边都 `push_back` 了两次（双向建图）：

```
g[x].push_back(y);
g[y].push_back(x);
```

这时候，`g` 内部没有任何方向，它只是一个纯粹的**无向图**。它只记录了一个基本事实：`x` 和 `y` 之间有一条通道，彼此是对等的。

**那么，树的“根节点”、“父亲”、“儿子”、“深度”这些概念，究竟是怎么凭空产生的？**

## 2. 蜕变推导：从“无向图”到“有向树”的三步转化

> 💡 **数学定义**：树（Tree）的本质，就是一个**连通且无环**的无向图。

正因为树本身就是图，所以我们不需要在存储结构上做任何特殊处理。把图“变成”树，靠的是 **DFS 遍历时施加的逻辑规则**。

### 第一步：提纽成树（指定根节点）

无向图原本像一张平铺在桌面上的网，没有上下之分。

一旦我们执行 `dfs(s, -1)`，就相当于**用手把节点 `s` 从网里提了起来**。

- 被手捏住的 `s` 变成了最高点（根节点，深度为 1）。
    
- 与 `s` 直接相连的节点受重力下垂，自然成为了第二层（儿子辈）。
    
- 依此类推，整个网络的拓扑层级（深度 dep）在这一瞬间被全部赋予了物理意义。
    

### 第二步：斩断回头路（关键所在）

当我们处在某个节点 `x` 时，我们去遍历它的邻接表 `g[x]`（即 `x` 的所有邻居）。

因为树**没有环**，所以对于节点 `x` 来说，它的邻居只可能包含两种身份：

1. **生它的人**：刚才把它搜出来的那个节点，即父亲 `fa`（上一层）。
    
2. **它生的人**：还没被访问过的、挂在它下面的节点，即儿子们（下一层）。
    

因此，代码里这句看似简单的判断：

C++

```
if (y != fa)
```

**它的物理意义是：斩断回头路。**

只要排除了那个送我过来的父亲 `fa`，剩下的所有邻居 `y` 就**必然且只能是 `x` 的亲生儿子**。

### 第三步：顺流而下（递归定型）

理清了父子关系后，我们就可以顺理成章地给儿子下达定义：

C++

```
dep[y] = dep[x] + 1; // 儿子的深度由父亲决定
dfs(y, x);           // 顺着儿子继续向下蔓延，同时告诉儿子：“我是你的父亲 x”
```

通过这种水流一般的 DFS 蔓延，原本混乱的无向图在逻辑上被完全梳理成了一棵方向明确、层级严密的**有向树**。

## 3. 为什么可以用 `this auto&& dfs` 优雅递归？

在这个 DFS 中，我们需要把“当前节点 `x`”和“父亲节点 `fa`”一路传下去。在 C++23 之前，Lambda 表达式想调用自身非常恶心。而现代 C++ 引入的 `(this auto&& dfs, ...)` 机制极其巧妙：

1. **打破闭环**：Lambda 本身是没有名字的匿名的函数对象。`this auto&& dfs` 相当于在 Lambda 内部硬生生开辟了一个引用，把**它自己这个对象**作为第一个参数传给了自己。
    
2. **调用解耦**：在内部递归时，写 `dfs(y, x)` 就能直接往下走。外部调用 `dfs(s, -1)` 时，编译器会自动把这个 Lambda 本身当做隐藏的第一个参数塞进去。
    
3. **零开销**：它不是 C++11 的 `std::function`（那种会带来动态内存分配和类型擦除的延迟），它在编译后会被优化得和普通的全局函数一样快。
    

## 📌 总结：放进 Obsidian 的一句话备忘

> 邻接表只负责记录**“谁和谁相邻”**。 树的形态不是存出来的，而是**利用树无环的特性，在 DFS 遍历中通过 `if (y != fa)` 排除父亲、确立层级，“走”出来的。**
